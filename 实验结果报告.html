结论速览（先看这四条）

  1. 只有"迁移学习"这一个变量是真的。 单次划分 预训练 − 从零 = +0.2300 ± 0.1151（5/5 种子）； 5 折池化 +0.2700 ± 0.0361（3/3 种子）。 两种分辨率、两套方法都指向同一结论，且训练时间只要 1/5。
  2. 数据增强在这份数据上没有任何收益。 5 轮 −0.0200、15 轮 −0.0100、 池化 −0.0033——三次方向一致都是负的。 这与指导书"增强提升泛化"的预期相反：80 张训练样本太少， 增强换来的方差收益抵不过信息稀释。
  3. 模型选型无意义。 四个预训练模型（AlexNet 冻结 / ResNet18 / MobileNetV3-S / ShuffleNetV2） 池化后全部落在 0.9033–0.9233，最大差距 2 张图。
  4. 指导书"六步对比表"里的多数差异其实是噪声。 验证集只有 20 张（1 个样本 = 5%），而各配置的标准差就有 0.05~0.10。 单次运行得出的"0.85 vs 0.90 vs 0.95"不具备统计意义—— 本报告第三节的「ShuffleNet 明显更差」就是被这一点骗到的，第六节已修正。

三、逐条解读

1 · 迁移学习：唯一站得住的结论

从零训练 0.68 ± 0.10 → 预训练冻结 0.91 ± 0.05，差值 +0.23， 且 5 个种子全部更好（连最差的一次预训练 0.85，也高于从零训练最好的一次 0.80）。 更有说服力的是训练 loss：从零训练降到 0.007（几乎背下 80 张图）， 预训练组是 0.0015 —— 两条曲线都在过拟合，但预训练组起点就高。

结论：指导书"小数据集从零训练学不出通用视觉特征"是本次实验中唯一被严格证实的论断。 而且实际水平比指导书预估的 0.65~0.80 更低——5 个种子里只有 1 次摸到 0.80。

2 · 数据增强：指导书预期落空

指导书说"增强提升泛化，数据越多越明显"。实测： 5 轮 −0.02（0/5 种子为正）， 15 轮 −0.01（1/5 种子为正）—— 加长轮数也没能翻盘。

但增强并非"没用"，它改变的是别的东西：训练 loss 从 0.267 升到 0.317（5 轮）—— 训练集变难了，模型确实没能像原来那样背下来。问题在于 80 张训练样本的信息量本来就不足， 再人为制造形变样本只会稀释有限的信息，而不是补充新的信息。

正确的表述是："在这份 100 张的数据上，未观察到数据增强带来准确率提升。" 而不是"增强没用"——增强的价值通常要在数据量足够时才显现， 本实验的规模恰好落在它失效的区间里。

3 · RandomErasing：我上一版的结论是错的

上一版报告基于单次运行写道"RandomErasing 有效（+0.06，4/5 种子）"。 补齐 5 个种子后，真实值是 +0.0100 ± 0.0224， 只有 1/5 个种子为正 —— 完全在噪声内，谈不上有效。

这个反例本身就是本报告最好的教材：单次运行 + 20 张验证集， 足以把纯噪声放大成一个看起来很有道理的故事。

4 · 冻结 vs 微调：上一版被"轮数不对等"骗了

上一版报告对比的是"冻结 30 轮 = 0.95"vs"微调 5 轮 = 0.90"，据此得出"冻结更好"。 这次把轮数拉平（都是 5 轮）后：0.91 vs 0.86，差值 +0.05 ± 0.06，3/5 —— 打平。

不过微调的训练 loss 是 0.264，而冻结只有 0.0015：冻结组几乎瞬间就把分类头训完了（第 1 轮就是 0.95）， 微调组则还在缓慢下降。所以两者的差别不在"能不能学会"，而在 收敛速度和计算成本——冻结只反传最后一层，微调要反传全部 5701 万参数。

现象数据
验证集粒度 20 张 → 1 个样本 = 5%，所有准确率都是 0.05 的整数倍

单跑认为 ShuffleNet 差 0.14 → 5 折池化后只差 0.0067（差 20 倍）

经验法则：差值 < 2 个验证样本（< 0.10）时不要下结论。 想把分辨率提上去，用 step8_crossval.py——结果见下一节。

六、5 折交叉验证（已跑完 · 分辨率 1%）

这一节推翻了第三节的一个结论

验证集从 20 张扩到 100 张（池化）后，分辨率由 5% 细化到 1%。 两条结果：迁移学习依然成立，而且差距更大（+0.23 → +0.27）； 而「ShuffleNet 明显更差」是单次划分的假象—— CV 下它与 ResNet18 只差 0.7%（0.9033 vs 0.9133）， 单次划分时看到的 0.14 差距（0.74 vs 0.88）纯粹是那 20 张验证集抽得不巧。

6.5 最终结论（合并 50 次消融 + 90 次交叉验证）

  1. 迁移学习是唯一站得住的结论。 从零 0.6533 → 预训练 0.90+，差 +0.27，3/3 种子一致， 且训练时间只要 1/5（10.9s vs 54.5s）。
  2. 数据增强在这份 100 张数据上没用，甚至略微有害。 两种分辨率、两种轮数下 Δ 都是负的（−0.02 / −0.003 / −0.01）， 虽然都在噪声内，但方向四次一致——不是"有效但测不出"，是"确实没帮助"。
  3. 模型选型无意义。四个预训练模型全落在 0.90–0.92， 最大的差距只有 2 张图。
  4. 指导书"六步对比表"里的大部分差异是噪声。 真正可信的只有第一条。

七、可复现性：两个把结果搞错的坑

坑 1 · 消融矩阵漏抄超参

第一版 step7_ablation.py 的配置表里，前两个配置忘了写 lr，代码走了兜底默认值 1e-3，而指导书这两步是 1e-4 —— 差 10 倍。 结果"从零训练"被算成 0.52，比真实值 0.68 低了 0.16。 现在配置表里 lr 全部显式写出，并打印在汇总表里。

坑 2 · 每轮验证会悄悄改变 shuffle 顺序

step1_scratch.py 每轮都跑一次验证，而消融的循环不验证。 表面看只是少了一次评估，但 DataLoader 的每个迭代器都会用全局随机数 生成 base_seed —— 少迭代一次，就从第 2 轮起 shuffle 顺序分叉， 同一个 seed 跑出不同结果（0.80 vs 0.75）。

已用 _diag_rng.py 验证：两条路径首个 batch 的标签完全相同， 最终准确率却不同 —— 精确定位到"从第 2 轮起分叉"。 修正方式是让消融也每轮验证，与各脚本协议对齐。

对齐后的自检结果

消融矩阵里 seed=42 的那一格，现在能精确复现各脚本单跑的值： 1→0.80、2→0.95、3→0.90、4→0.90、6→0.90、7→0.75。 这是"控制变量"真正生效的标志。

八、文末思考题

1. 把冻结改为全模型微调（lr=1e-5），准确率和训练时间如何变化？

轮数拉平到 5 轮后：冻结 0.91 ± 0.05， 微调 0.86 ± 0.07，差值 +0.05 ± 0.06（3/5 种子） —— 没有显著差异。

时间上差异明确：冻结只反传分类头，微调要反传全部 5701 万参数， 每轮耗时约 1.3 倍。但微调的训练 loss（0.264）远高于冻结（0.0015）， 说明微调仍在持续学习、还有下降空间，而冻结组第 1 轮就收敛到 0.95 了。

结论：小样本场景冻结是性价比更高的默认选择；微调的潜力更大但需要更多轮数 和更多数据才能兑现。（注意：本实验微调只跑了 5 轮，不能据此否定微调。）

2. 把数据增强再加强（如 RandomErasing），置信度分布如何变化？

已实测（配置 5）：准确率 0.89 ± 0.08，相对基础增强 +0.01 ± 0.02（1/5 种子）—— 准确率上没有可观察的变化。

但训练 loss 从 0.317 升到 0.378，是所有配置里最高的，说明任务被显著加难了。 结合"准确率不变"，可以推断模型转而依赖更多部位的综合证据做判断， 即置信度分布向中间收敛——错误样本不再给出 90%+ 的盲目高置信度。 这通常意味着更好的概率校准，但对本实验的准确率指标没有帮助。

要严格验证这一点，需要额外记录每张验证图的预测概率并画直方图。 工程包里可以在此基础上加一个置信度收集函数，这里不做展开。

3. 用 FastAPI 把 predict 封装成 HTTP 接口，写微信小程序前端调用

思路与指导书一致，关键是把第六步的 predict 逻辑从 Gradio 里剥出来：

# server.py —— pip install fastapi uvicorn python-multipart
from fastapi import FastAPI, UploadFile, File
import io
from PIL import Image
# ... 复用 step6_app 的 net / transform / CLASSES / DEVICE ...

app = FastAPI()

@app.post("/predict")
async def predict_api(file: UploadFile = File(...)):
    img = Image.open(io.BytesIO(await file.read())).convert("RGB")
    x = transform(img).unsqueeze(0)
    with torch.no_grad():
        probs = torch.softmax(net(x.to(DEVICE)), dim=1)[0].cpu()
    conf, pred = probs.max(0)
    return {"label": int(pred), "name": CLASSES[int(pred)],
            "confidence": round(float(conf), 4),
            "probs": [round(float(p), 4) for p in probs]}
# 启动：uvicorn server:app --host 0.0.0.0 --port 8000
# 小程序端：
wx.chooseMedia({ count: 1, mediaType: ['image'], success(res) {
  wx.uploadFile({
    url: 'http://<电脑IP>:8000/predict',
    filePath: res.tempFiles[0].tempFilePath,
    name: 'file',
    success: r => console.log(JSON.parse(r.data))
  })
}})

两个真实的坑：① 微信小程序只允许请求 https 且域名需在后台白名单备案， 局域网 http://192.168.x.x 只能在开发者工具里勾选"不校验合法域名"调试， 真机预览会失败——要么上内网穿透（ngrok/frp），要么正式备案域名。 ② uvicorn --host 0.0.0.0 会监听全部网卡，Windows 防火墙需放行， 且不要在公网环境裸跑，至少加一层鉴权。
